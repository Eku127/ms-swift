# VLN 模型在 ms-swift 中的设计文档

本文档描述在 ms-swift 框架中实现视觉语言导航（VLN）模型的设计方案，参考 StreamVLN 的核心设计理念。

## 核心设计需求

### 1. 动作预测机制
- **每一帧预测未来四步动作**：模型根据当前观察预测未来 N 步（默认 N=4）的导航动作序列
- **动作格式**：动作序列转换为文本格式（如 "↑←→↑"），作为模型的输出标签

### 2. 帧分类处理
- **当前帧**：最新的观察帧，用于预测下一步动作
- **历史帧**：从轨迹开始到当前片段的历史观察帧，提供上下文信息
- **分离处理**：当前帧和历史帧需要不同的 token 压缩策略

### 3. Token 压缩策略
- **当前帧**：使用标准的 Qwen 视觉预处理器，token 数量与标准处理一致
- **历史帧**：通过空间池化（spatial pooling）减少 token 数量，降低计算成本
- **可配置参数**：通过 `current_stride` 和 `history_stride` 参数控制压缩程度

### 4. 历史帧采样
- **采样策略**：从历史轨迹中采样固定数量的历史帧（`num_history` 参数）
- **采样方式**：支持均匀采样或随机采样
- **采样时机**：在数据预处理阶段完成采样

## 架构设计

### 是否需要自定义模型？

**答案：需要自定义模型**

**原因**：
1. **差异化处理**：需要区分当前帧和历史帧的处理逻辑
2. **Token 压缩**：历史帧需要特殊的空间池化处理
3. **特征融合**：需要将历史帧特征和当前帧特征融合到对话序列中
4. **特殊 Token**：需要使用 `<memory>` token 表示历史帧特征

### 模型架构组件

#### 1. 视觉编码器（Vision Tower）
- **基础组件**：复用 Qwen2.5-VL 的视觉编码器（SigLIP）
- **功能**：将图像转换为视觉特征
- **输出**：每张图像生成固定数量的 patch tokens（如 27×27=729 tokens）

#### 2. 投影层（MM Projector）
- **功能**：将视觉特征投影到语言模型的特征空间
- **处理**：对所有帧（历史帧和当前帧）都经过投影层

#### 3. 空间池化层（Spatial Pooling）
- **当前帧池化**：
  - 输入：投影后的当前帧特征（如 729 tokens）
  - 池化方式：根据 `current_stride` 参数进行空间池化
  - 输出：压缩后的 token 数量（如 729 → 196 tokens，stride=2）
  
- **历史帧池化**：
  - 输入：投影后的历史帧特征
  - 池化方式：根据 `history_stride` 参数进行空间池化
  - 输出：进一步压缩的 token 数量（如 729 → 196 tokens，stride=2）
  - **特点**：历史帧的压缩程度通常大于当前帧

#### 4. 特征融合机制
- **当前帧特征**：直接插入到对话序列中的 `<image>` token 位置
- **历史帧特征**：插入到对话序列中的 `<memory>` token 位置
- **融合方式**：在 token embedding 层进行特征替换

## 数据流设计

### 训练阶段数据流

```
输入数据
  ↓
【数据预处理】
  ├─ 历史帧采样（num_history 帧）
  ├─ 当前帧采样（num_frames 帧，按 stride 采样）
  └─ 动作序列提取（未来 num_future_steps 步）
  ↓
【视觉编码】
  ├─ 历史帧 → Vision Tower → MM Projector → Spatial Pooling (history_stride)
  └─ 当前帧 → Vision Tower → MM Projector → Spatial Pooling (current_stride)
  ↓
【特征融合】
  ├─ 历史帧特征 → 替换 <memory> token
  └─ 当前帧特征 → 替换 <image> token
  ↓
【语言模型处理】
  └─ 生成动作序列文本
```

### 关键参数

| 参数名 | 默认值 | 说明 |
|--------|--------|------|
| `num_future_steps` | 4 | 预测未来动作的步数 |
| `num_frames` | 32 | 当前片段的帧数 |
| `num_history` | 8 | 历史帧采样数量 |
| `current_stride` | 2 | 当前帧的空间池化步长 |
| `history_stride` | 2 | 历史帧的空间池化步长 |

## 实现方案

### 方案一：基于 Qwen2.5-VL 扩展（推荐）

**思路**：继承 Qwen2.5-VL 的模型结构，添加自定义的视觉处理逻辑

**优势**：
- 复用现有的视觉编码器和投影层
- 只需添加空间池化和特征融合逻辑
- 与 ms-swift 的模型注册机制兼容

**需要实现的核心功能**：
1. **自定义视觉编码方法**：
   - 区分历史帧和当前帧
   - 对历史帧和当前帧应用不同的池化策略
   - 返回分离的历史特征和当前特征

2. **自定义 Token 替换逻辑**：
   - 在 `prepare_inputs_labels_for_multimodal` 方法中
   - 识别 `<memory>` token 和 `<image>` token
   - 分别替换为历史特征和当前特征

3. **空间池化实现**：
   - 支持平均池化、最大池化、双线性插值等模式
   - 可配置的 stride 参数

### 方案二：完全自定义模型

**思路**：从头实现完整的 VLN 模型架构

**优势**：
- 完全控制模型结构
- 可以自由设计特征融合方式

**劣势**：
- 实现复杂度高
- 需要重新实现很多基础功能
- 与 ms-swift 的集成可能更复杂

**推荐**：采用方案一

## 关键设计决策

### 1. 历史帧和当前帧的区分

**实现方式**：
- 在数据预处理阶段，明确标记哪些是历史帧，哪些是当前帧
- 通过 `time_ids` 参数传递帧的时间索引信息
- 模型根据 `time_ids` 判断帧的类型

**数据格式**：
- 输入：`images` 列表，按顺序排列（历史帧在前，当前帧在后）
- 元数据：`time_ids` 列表，标记每帧的时间索引
- 分割点：`num_history` 参数确定历史帧和当前帧的分界

### 2. Token 压缩策略

**当前帧压缩**：
- 目标：保持与标准 Qwen2.5-VL 一致的 token 数量
- 方法：使用较小的 stride（如 stride=2），轻微压缩
- 原因：当前帧是最重要的信息，需要保留更多细节

**历史帧压缩**：
- 目标：大幅减少 token 数量，降低计算成本
- 方法：使用较大的 stride（如 stride=2 或更大），显著压缩
- 原因：历史帧提供上下文，不需要太多细节

**池化模式选择**：
- **平均池化（average）**：保留整体信息，适合大多数场景
- **最大池化（max）**：保留突出特征，可能丢失细节
- **双线性插值（bilinear）**：平滑过渡，保持空间连续性

### 3. 特征融合位置

**融合时机**：
- 在视觉编码和投影之后
- 在输入语言模型之前
- 替换对话序列中的特殊 token

**融合方式**：
- `<image>` token → 当前帧特征（多帧特征按顺序插入）
- `<memory>` token → 历史帧特征（所有历史帧特征拼接后插入）

### 4. 历史帧采样策略

**均匀采样**：
- 从历史轨迹中均匀采样 `num_history` 帧
- 优点：覆盖整个历史范围，提供完整上下文
- 缺点：可能丢失重要时刻的信息

**随机采样**：
- 从历史轨迹中随机采样 `num_history` 帧
- 优点：增加数据多样性，提高模型泛化能力
- 缺点：可能遗漏关键信息

**推荐**：训练时使用随机采样，推理时使用均匀采样

## 与 ms-swift 的集成

### 1. 模型注册

**注册方式**：
- 创建自定义模型类，继承 ms-swift 的多模态模型基类
- 使用 `register_model()` 注册模型
- 配置 `model_arch` 参数，指定视觉编码器和投影层的路径

**关键配置**：
- `model_type`: 自定义类型名（如 "qwen2.5-vl-vln"）
- `is_multimodal`: True
- `model_arch`: 指定 vision_tower 和 mm_projector 的路径

### 2. Template 定制

**需要定制的内容**：
- 支持 `<memory>` token 的处理
- 支持多图像输入的 token 替换逻辑
- 自定义 `_encode` 方法，处理历史帧和当前帧的特征融合

### 3. 数据集集成

**数据格式**：
- 使用 ms-swift 标准格式（messages + images）
- 在 `images` 字段中包含历史帧和当前帧
- 通过元数据字段传递 `time_ids` 信息

**预处理**：
- 在数据集预处理器中实现历史帧采样
- 构建包含 `<memory>` 和 `<image>` token 的对话格式
- 确保图像顺序正确（历史帧在前，当前帧在后）

## 关键技术细节

### 1. Token 数量计算

**标准 Qwen2.5-VL**：
- 输入图像：384×384
- Patch 大小：14×14
- Token 数量：27×27 = 729 tokens

**当前帧（stride=2）**：
- 池化后：14×14 = 196 tokens
- 压缩比：729 / 196 ≈ 3.7

**历史帧（stride=2）**：
- 池化后：14×14 = 196 tokens（每帧）
- 总 token 数：num_history × 196 tokens
- 压缩比：与当前帧相同，但总数量取决于历史帧数

### 2. 内存优化

**挑战**：
- 多帧图像可能占用大量内存
- 历史帧特征需要缓存

**优化策略**：
- 使用梯度检查点（gradient checkpointing）
- 历史帧特征在投影后立即池化，减少内存占用
- 使用混合精度训练（bfloat16）

### 3. 训练效率

**批处理**：
- 不同样本的历史帧数量可能不同
- 需要动态 padding 或 masking
- 使用 attention mask 忽略 padding 位置

**数据加载**：
- 历史帧采样在数据预处理阶段完成
- 避免训练时的动态采样开销
- 使用多进程数据加载

## 预期效果

### 优势
1. **计算效率**：历史帧压缩减少 token 数量，降低计算成本
2. **上下文保持**：历史帧提供轨迹上下文，提高导航准确性
3. **灵活性**：可配置的参数允许调整压缩程度和采样策略
4. **兼容性**：基于 Qwen2.5-VL，与 ms-swift 框架良好集成

### 挑战
1. **实现复杂度**：需要自定义模型和 template
2. **调试难度**：多帧处理和特征融合的调试可能较复杂
3. **参数调优**：需要调整多个超参数（stride、num_history 等）
